# Known Limitations

Updated every milestone, and swept line by line at the end of M9. **Nothing external is live.**
Each row names the production replacement and who owns it next: *before launch* means a real
customer would be affected, *after pilot* means it can wait.

The honest summary: every flow in this product works end to end against mock adapters, with the
rules, the ledger and the guards all real. No money has ever moved, no SMS has ever been sent,
and no file has ever been stored. The list below is what stands between that and a real pilot.

| Media bytes | **real** | a local-disk storage adapter stores, serves and deletes the actual bytes behind signed, scoped, expiring grants. | Accessibility | **measured** | `npm run a11y` computes WCAG contrast for every pairing the app renders, reading the real palette so it cannot drift, and fails CI on a miss. Eight real contrast failures found and fixed (D-014). Icon-only controls are checked for labels, and literal hex text colours for AA | a screen-reader pass on a device | before launch |
| Screen-reader pass | **partly done** | the accessibility tree was read off the device, which is what a screen reader reads. No control was unnamed, confirming the static audit - but nine were announced **twice** (the control carried a name and its own text was exposed as well, so TalkBack said "Plumbing, Plumbing") and one label had a trailing comma. Fixed in `Button`, `Card`, `TabBar` and the booking tiles, and the mobile tests now find buttons by their accessible name, which is what proves it. What is still not done is *driving* TalkBack: reading order and where focus lands after a sheet closes cannot be read out of a dump | a TalkBack walkthrough | before launch |
| Load testing | **done for load, not soak** | 100 concurrent booking walks against real Postgres: 100/100 in 10.9s, 120 req/s, nothing over 3s, slowest p95 `provider/profile` at 1.6s. Nothing has run for hours, so a slow leak or an index degrading as tables fill would not have shown | a soak run | before launch |
| Mobile crash reporting | **implemented, mocked rail** | a hand-written Sentry envelope POST rather than the native SDK, so it adds no build complexity. Phone numbers, emails and bearer tokens are scrubbed from messages and stack frames before anything leaves the device. Without `EXPO_PUBLIC_SENTRY_DSN` it logs to the console and sends nothing | a DSN + a rehearsal | before launch |
| Offline queueing | **implemented** | status updates, chat, photos, completion and availability survive a dead connection and replay on reconnect, each with the idempotency key it was given. Money never queues: a person needs to watch a payment succeed or fail while looking at the screen. It is an allow-list, so a new endpoint is not silently queueable | - | - |
| Running more than one node | **supported** | scheduler exclusion via a Postgres advisory lock with the schedule itself in `scheduler_runs`, SSE fan-out over LISTEN/NOTIFY, and a shared counter for the OTP limits. Proven by tests that run two real nodes - against Postgres, two stores with two pools on one database. The earlier advice to run the scheduler on a single node is gone; it traded duplicate work for a single point of failure | - | - |
| Global rate limit | **per node, on purpose** | 300/minute is counted in process. It is fairness, not security - the limits that stop an attack count rows in `otp_challenges` and always did - and a database round trip on every request is a real cost to pay for a tidier number | shared counter, if abuse ever justifies it | after pilot |
| Ops report | **aggregates** | six whole-table aggregates. Previously it walked up to 500 customers and 200 jobs each with a ledger read per job, and **truncated in silence** past those limits, so an operator could not tell a quiet week from a missing thousand jobs. `providersVerified` and `providersSuspended` were hardcoded to zero | - | - |
| Container image | **written, never built** | `Dockerfile` is multi-stage, non-root, `tini` as PID 1. The riskiest parts were verified without Docker - the runtime dependency install run exactly as the image does it, the bundled server started against only those dependencies, and the health endpoints and healthcheck command exercised against it - which found two real bugs. The image build itself is unproven because Docker Desktop would not start in this environment | one `docker build` | before launch |
| Soak testing | **not done** | 100 concurrent booking walks pass against real Postgres at 121 req/s with nothing over 3s. Nothing has run for hours, so a slow leak, a connection that is never returned, or an index degrading as tables fill would not have appeared | a soak run | before launch |

Before this a customer described a leaking tap and submitted with no idea whether the answer was three hundred rupees or three thousand | - | - |
